# sys_tune v1.2 - аудит и доработка модуля

Телефон: OnePlus 7 (guacamoleb), LineageOS 24.0, стоковое ядро
`4.14.357-openela-perf-g0521dc291cf1` (APatch 11282). Модуль правит
параметры userspace, ядро менять не нужно.

## Что было в v1.1 и что не работало

| пункт v1.1 | факт |
|---|---|
| `device_config put ... max_cached_processes 512` в post-fs-data | **всегда падал с rc=20**: сервис DeviceConfig живёт в system_server, в post-fs-data он ещё не поднят. Значение 512 держалось только до перезагрузки. |
| проверка результата | не было: модуль писал значение и не сверял его |
| I/O-планировщик cfq -> deadline | работает |
| `tcp_slow_start_after_idle = 0` | работает, измерено -9% к "до первого байта" |

`dumpsys activity` сейчас показывает `max_cached_processes=1024` (дефолт AOSP)
и `CUR_MAX_CACHED_PROCESSES=512` (то, что держится в памяти с прошлого раза).

## Замеры на этом телефоне

### Writeback (главное изменение)

Запись 256 МБ + `sync`, три замера каждый:

| dirty_ratio / background / expire | замеры, мс | среднее |
|---|---|---|
| сток 20 / 10 / 30 с | 1004, 1001, 774 | 926 |
| 10 / 3 / 15 с | 874, 643, 636 | 718 |
| 10 / 3 / 15 с (повтор после установки модуля) | 489, 677, 651, 629 | 612 |

Причина: на 11.7 ГБ RAM стоковые 20% = до 2.3 ГБ грязных страниц.
Writeback начинается слишком поздно, всплеск записи на UFS (300 МБ/с)
встаёт колом - интерфейс в это время подтормаживает.

### Что проверили и НЕ стали менять

| кандидат | замер/факт | решение |
|---|---|---|
| `zram` (2.3 ГБ, lzo) | занято 27 МБ из 2.3 ГБ, PSI memory = 0 | не трогаем |
| `max_cached_processes` | в кэше AMS 265-268 процессов при лимите 1024 - лимит недостижим | по умолчанию выключено (0), чинится правильно |
| `nr_requests` 64/128/256 | 24.5-25.4k IOPS, разница в шуме | не трогаем |
| `uclamp`/boost | `/dev/stune/top-app/schedtune.boost = 30` уже стоит штатно | не трогаем (система сама управляет) |
| `tcp_fastopen` | 1 (клиент) - стоковое значение | не трогаем |
| `swappiness` / `page-cluster` | 100 / 0 - корректно для zram | фиксируем page-cluster=0 явно |
| CPU governor / boost | schedutil, Android сам ставит top-app boost | не трогаем |
| `read_ahead_kb` | 128 КБ, UFS тянет 808-883 МБ/с | не трогаем |

## Что добавили в v1.2

1. Writeback-тюнинг (измерено выше).
2. `page-cluster=0` и `tcp_slow_start_after_idle=0` в post-fs-data - чтобы
   действовало с первого сетевого трафика.
3. Каждая настройка проверяется чтением обратно, результат пишется в лог.
4. `device_config` переехал в late_start с ожиданием `sys.boot_completed=1`
   и повторами. Включается переменной `MAX_CACHED_PROCESSES` (по умолчанию 0 -
   не трогать).
5. Опция `CHARGE_LIMIT` (charge_control_limit, 0..4, по умолчанию 0 -
   не трогать).
6. `uninstall.sh` - возврат стоковых значений при удалении модуля.
7. Срез состояния в лог (loadavg, PSI, cached-процессы, zram, свободная RAM)
   - чтобы сравнивать "до/после".

## Где настоящее узкое место

Не в ядре и не в модуле:

* 265-268 процессов в кэше AMS, 3-4 ГБ RSS; топ: TikTok 655 МБ,
  Wellbeing 427 МБ, YouTube 285 МБ, GMS 445 МБ, Тинькофф 437 МБ.
* loadavg 2.1-3.5 в покое на 8 ядер.
* PSI после покоя: cpu 0%, io some 2.16% / full 1.32%, memory 0%.

То есть при живых приложениях телефон упирается в фоновую активность
(особенно I/O), а не в параметры ядра.

## Откат

* удалить модуль - сработает `uninstall.sh`;
* или создать `/data/adb/modules/sys_tune/disable`;
* бэкап v1.1: `/data/local/tmp/sys_tune_backup_v1.1/`;
* лог: `/data/local/tmp/sys-tune.log`.

# v1.3 — планировщик: что дало, что нет

Методика: `lat.c` (16 потоков по 500 мкс сна, 8 «жрущих» потоков в фоне,
p50/p90/p99/p99.9/max), холодный запуск Settings через `am start -W` после
`force-stop`, `cpu` (300 млн вызовов) как контроль пропускной способности.
Все сравнения — **парные** (base/вариант через раз).

## Хвост задержек пробуждения (главный результат)

7 пар, `sched_wakeup_granularity_ns` 2 мс -> 0.5 мс:

| пара | base p99.9 / max, мкс | wake p99.9 / max, мкс |
|---|---|---|
| 1 | 431 / 24 441 | 507 / 3 285 |
| 2 | 451 / 7 910 | 476 / 1 931 |
| 3 | 613 / 4 191 | 328 / 2 333 |
| 4 | 672 / 74 275 | 297 / 3 256 |
| 5 | 1086 / 27 867 | 320 / 3 589 |
| 6 | 453 / 7 969 | 791 / 2 111 |
| 7 | 428 / 16 306 | 430 / 1 954 |

Медиана худшей задержки: **16 306 -> 2 333 мкс (в 7 раз)**.
p50/p90 не меняются (89->90, 118->118). CPU 697 -> 694 мс (ноль потерь).

## Что проверено и отвергнуто

| режим | запуск Settings под нагрузкой (медиана) | вывод |
|---|---|---|
| base | 435 / 406 / 422 / 397 / 461 | — |
| balance (KTweak как есть) | 454 | не лучше |
| latency (1 мс / 0.1 мс / nr_migrate 4) | 508 | **хуже на ~20 %** |
| hybrid (хвост без частот) | 497 | тоже хуже |
| wake (только порог вытеснения) | 413 / 608 | в пределах шума |

Причина: `sched_latency_ns` 10->1 мс и `min_granularity` 3->0.1 мс дают
слишком частые переключения — хвост лучше, среднее хуже.
`schedutil up_rate_limit_us` 500->4000 (KTweak balance) — частота разгоняется
медленнее, запуск приложений хуже. `sched_nr_migrate` 32->4 — то же.

## nr_requests 128 -> 32

fio 4K randwrite, 4 потока, direct, 128 МБ: 128 -> 24.9/25.3/30.0k IOPS,
32 -> 25.2/33.7/25.0k IOPS. Потерь нет.

## Итог v1.3

Включено: `sched_wakeup_granularity_ns=500000`, `sched_migration_cost_ns=5000000`,
`sched_child_runs_first=1`, `sched_schedstats=0`, `perf_cpu_time_max_percent=5`,
`vm.stat_interval=10`, `queue/iostats=0`, `queue/nr_requests=32`.

Не включено: `sched_latency_ns`/`min_granularity` (плата — запуск приложений),
rate limits schedutil, `sched_nr_migrate=4`, `tcp_syncookies=0`, `add_random=0`.

Честно: это ровность в плохие моменты (нет пропущенных кадров из-за
планировщика при фоновой нагрузке), а не ускорение. Средние значения,
пропускная способность и запуск приложений не изменились.
